# Issue 分类与 PR 对账

## Issue 分类

| 分类 | 例子 | 必须动作 |
|---|---|---|
| 局部 bug | 单个接口返回错误、单个状态条件判断错误、单个页面调用参数错误 | 最小修复，补回归测试，同步相关 spec |
| 设计变更 | 新支付渠道、退款流程重排、订单复用规则变化、幂等策略变化 | 先写 `spec/planned/`，确认契约和验收标准后再实现 |
| 公共接口或兼容影响 | HTTP 路径/响应结构变化、状态文案变化、DB 字段变化、MQ 名称变化、微信/支付宝回调响应变化 | 更新契约、兼容影响和特征测试；说明旧调用方如何处理 |
| 多 issue 同根因 | 多个支付通知问题都来自同一幂等规则；多个退款问题都来自同一状态汇总规则 | 合并分析根因，先写统一 spec，避免逐个打补丁 |

## PR 合并前 Spec 对账清单

- [ ] PR 描述写明 issue 分类。
- [ ] PR 关联了对应 spec；没有 spec 时说明“不适用”的理由。
- [ ] 涉及设计变更时，`spec/planned/` 已描述目标契约和验收标准。
- [ ] 已实现行为对应 `spec/implemented/`，并填写实现锚点。
- [ ] public API、响应结构、状态值、DB、Redis、RabbitMQ、配置、前端调用和第三方回调的兼容影响已检查。
- [ ] 特征测试或回归测试覆盖了行为变化或保持不变的现状。
- [ ] `spec/README.md` 状态索引已更新。
- [ ] 验证命令和结果写入 PR，例如 `cd payment-demo-go && go test ./...`。
