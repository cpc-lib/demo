## 2. 合并决定

| 主题 | 生效规则 |
|---|---|
| 商品管理 | 保留 t_product 和 ADMIN 上下架、库存调整、流水 API；每个商品一个默认 SKU，不建设多规格编辑器或多仓 |
| 普通用户商品 | 下架不可见/不可购买；零库存展示售罄，前后端均禁止加购 |
| 购物车 | 不预占，失效行可移除；结算创建订单才锁库存 |
| 库存事实 | t_sku_stock 为唯一在线余额；独立 Reservation 与业务幂等库存流水 |
| 订单幂等 | 后端签发 USER 绑定键；未使用键首次提交窗口 120 秒；COMPLETED 超时仍返回原订单 |
| 多次支付 | Order 1:N PaymentOrder；有效成交只允许一笔，所有真实到账均保存 |
| 支付号码 | 业务 orderNo 不变；新渠道 out_trade_no 使用 paymentNo；历史渠道号码显式映射、不重写 |
| 支付成功 | 全部预占完整性校验及整单库存预检后，一次性实扣；远程通知与查单共用完成服务 |
| 缺库存自动退款 | 整单无部分实扣，持久化该支付单全额补偿＋Outbox；渠道成功后只安全释放未实扣预占 |
| 重复/迟到付款 | 仅退对应异常支付单资金；不占正常商品退款额度、不增加商品已退数量、不回库 |
| 退款金额 | 商品按订单快照和数量计算；支持冻结金额/数量、剩余金额尾差和独立原运费规则 |
| 审批与资金 | 审批只更新审核状态和 Outbox；渠道在事务外调用，未知结果保留冻结额度 |
| 未发货取消回库 | 不可逆取消履约后授权回库，可早于渠道退款成功；与发货条件更新互斥 |
| 退货回库 | 根据真实验收的可再次销售数量回库，按验收批次幂等；不可售不增加可用库存 |
| 仅退款/差价 | 不回库；差价不占数量，同一明细差价与数量退款禁止同时未决 |
| 消息幂等 | Outbox 可靠确认＋Inbox 可恢复租约；BUSY 必须重试，CONSUMED 才能直接成功 |
| 双端 | React/Vue 状态、字段、退款选择、管理能力与权限同步；移除友情链接及版权行 |
| ADMIN 边界 | 延续禁止加购/下单/商品支付/用户退款；可审批、发货、验收、查单和运营商品 |

“只有渠道退款成功才处理库存”仍适用于 PAYMENT_STOCK_SHORTAGE 的安全释放分支；不再泛化到有实物取消/验收证据的售后回库。

## 3. 已修正的设计冲突

- 回库上限来自取消确认或验收可售数量，不再用 restocked_qty <= refunded_qty；付款退款和实物回库允许先后独立完成。
- 系统退款幂等绑定 paymentNo + refundType，一个订单多笔异常付款分别补偿，不能只按 orderNo 去重。
- 第二笔同渠道真实到账不能被原 (order_no,payment_type) 支付流水唯一键吞掉；对账同步转到支付单维度。
- 创建退款、拒绝和成功必须处理全部适用层级的额度，包括原支付单；渠道超时不解冻。
- 支付库存异常保留 ANOMALY_PENDING 隔离规则，不能利用其他订单后来锁入的库存做释放。
- 退款验收使用 receiptRequestId；同一退款明细第二个合法批次不能被误去重。
- 关键业务和 Outbox 同事务；所有时序中提交后直接发 MQ 的步骤由 Outbox 发布器承担。
- 数据库、Redis、RabbitMQ 不确定结果不应伪装为付款/退款成功或确认关闭。

## 4. 兼容版本与 API

本次扩大涉及公开 API 和模型变更，目标为 v0.6.0。保持回调 URL、签名/应答协议及 R 响应外壳；新支付单接口、独立订单状态、退款类型、验收进度和 long 分金额由两套前端同步适配。

保留 POST /api/order-info/idempotency-keys，新增业务订单支付尝试/查单、最小发货与验收、ADMIN 差价/原运费退款入口；具体路径和请求字段以统一设计第 9 节为准。

继续废弃旧按金额用户申请：删除旧 RefundRequest 及渠道专用申请 URL、路径参数申请 URL；不得删退款通知端点。历史金额退款记录是迁移数据，不是继续保留旧申请 API 的理由。

存量升级必须使用独立增量迁移与核对材料，禁止运行含 DROP 的初始化脚本。缺少付款、库存或退款明细证据的历史订单进入 LEGACY_REVIEW，不按当前商品价格推算，不自动制造明细或回库。执行数据库变更另行授权。
